	    Nesse trabalho para desenvolver o sistema de monitoramento para prevenção de incêndios dentro do cenário de um campus da UFPB, foi escolhida a arquitetura de redes 5G e testar em um ambiente emulado. O macOS foi é sistema operacional e para simular o ambiente foi utilizado o Mininet no Docker \cite{mininet} para facilitar o desenvolvimento e portabilidade do projeto. O sistema utilizado no contêiner foi o Ubuntu 22.04, possibilitando a emulação e construção de quatro switches configurados usando o OpenVSwitch \cite{pfaff2015ovs}.

        Nessa simulação, a topologia é constituída por três ambientes que são monitorados por sensores e câmeras. No caso dos sensores, é utilizado o uRLLC para priorizar a comunicação com baixa latência até o servidor central e, para o monitoramento com as câmeras, foi utilizado o eMBB, para lidar com um tráfego maior já que os dados processados são de vídeo. Com a biblioteca scapy \cite{scapy} foi possível a simulação dos tráfegos em TCP para as comunicações uRLLC, e UDP para eMBB que usou também o iperf3 \cite{iperf}, responsável para gerar uma carga maior de dados, validando os testes. Para medir a latência e poder monitorar, o seguinte cálculo utilizado foi: (tempo\_recebimento - tempo\_envio) * 1000. Outro método importante no projeto é o uso do controlador closed loop, com ele é possível monitorar o estado das conexões e suas respectivas latências de forma contínua para tomar a decisão de quando deve priorizar cada tráfego. Para avaliar os resultados foram usadas as bibliotecas python: numpy para trabalhar com dados estatísticos e; matplotlib para gerar gráficos.

		\section{Proposta}
		% ===================================================================
		
		A proposta desse projeto é desenvolver um sistema para prevenir incêndios. Desenvolvido em redes 5G, o sistema propõe utilizar sensores e câmeras para mitigar e prevenir possíveis incêndios usando tecnologia de comunicação ultra confiável e de banda larga. 

        \subsection{Ambientes de Monitoramento}
        
        Os ambientes que irão ser monitorados na simulação, são a biblioteca, reitoria e laboratórios. O sensores aplicados vão identificar a temperatura do ambiente, umidade, fumaça, chamas e gás. A câmera irá ativar o monitoramento assim que detectar algumas anomalias identificadas pelos sensores e que possam está relacionados a possíveis princípios de incêndios.

        Para os sensores a tecnologia usada dentro do contexto das redes 5G, garantindo o mínimo de tempo possível de entrega para uma central de monitoramento é o uRLLC (Comunicação Ultra Confiável de Baixa Latência) \cite{3gpp23501,itu2017m2410}, com essa aplicação a comunicação irá chegar com valor de tempo igual ou abaixo de 5 milissegundos, dentro do contexto que o projeto é proposto. O monitoramento com as câmeras será utilizado também tecnologia de redes 5G, o eMBB (Comunicação Massiva entre Dispositivos), com essa aplicação será possível enviar dados com uma carga maior de informação - imagens - que poderão gerar mais valor na identificação e solução dos elementos para prevenir incêndios no local.

        A comunicação dos dispositivos de cada local estão conectados a quatro switchs em linha com essa arquitetura simulada usando o Mininet que emula a rede 5G. Um switch fica responsável por conectar os servidores de monitoramento de sensores e de câmeras, cada um processando dados de forma que não sobrecarregue ou gere perdas de dados na comunicação.
        
        \subsection{Tráfegos uRLLC e eMBB}
        
        O tráfego da rede uRLLC que passam as mensagens TCP pela porta 5000 e eMBB onde passa o fluxo relacionado a vídeo é gerado pelo o iperf3 através das portas 5001-5003, são simulações onde atesta os resultado e objetivos alcançados da proposta do projeto. Um mecânismo importante nessa construção é o QoS (Qualidade de Serviço) adaptativo \cite{olegario2024qos5g}, o qual cria filas, onde a fila 0 representa o tráfego uRLLC e a fila 1 representa o eMBB,  e essas regras são implementadas graças ao OpenFlow \cite{mckeown2008openflow} dentro dos switchs OVS \cite{pfaff2015ovs}. E como funciona? a fila uRLLC tem banda reservada e o eMBB a banda é ajustável pois não tem prioridade como a anterior.

		\sugestao{Conferir a numeração das filas antes da submissão: na implementação executada, a fila 1 foi reservada ao uRLLC e a fila 0 ao eMBB. A observação deve ser usada para revisar a descrição, caso o mapeamento apresentado no parágrafo não seja intencional.}

        \subsection{Closed Loop e Ajustes de Latência}
        
        Para assegurar o monitoramento é utilizado o closed loop \cite{simao2025mecanismo}, é com ele que o ciclo segue a seguinte sequência: a central observa cada mensagem uRLLC e mede a latência; o controlador toma a decisão de medir o limite de 5 ms, e se esse limite ulltrapassar o máximo, reduz a taxa máxima das filas eMBB de 20 para 2 Mbit/s \cite{linuxhtb} aliviando a rede para o uRLCC. Todo esse processo é repetido e verificado graças ao closed loop para manter uma rede estável principalemnte para os sensores.

        No caso do tráfego eMBB ser limitado ou ajustado para priorizar o tráfego uRLLC, é para o tráfego das câmeras não ser interrompido e manter a rede completamente ativa. O monitor não apenas ajusta as prioridades só baseado na primeira latência acima de 5 ms, para ativar e fazer os ajustes é usado um método chamado histerese, se houver limites acima de 5 ms duas vezes consecutivas então é ativado para ajustar o tráfego e quando voltar ao normal espera três medições sequenciais abaixo de 5 ms para desativar a proteção.

		\section{Avalia\c{c}\~ao}
		% ===================================================================
		
		O projeto seguiu alguns pilares para demonstrar os resultados produzidos para a avaliação, são eles quatro cenários: Isolado; Sem QoS; QoS Estático e; Closed Loop. 
		
		\subsection{Configura\c{c}\~ao Experimental}

        O ambiente dos experimentos é todo virtualizado, desde os switches até os sensores. Tudo dentro do docker, usando linux e rodando no MacOS.  Foram realizado diversos testes, dos quatro cenários foram feito cinco em cada, totalizando uma bateria de 20 testes. 

        \subsection{Resultados e Discussões}
        
        O primeiro cenário testado foi o isolado, nela apenas o tráfego uRLLC está ativo sem concorrer com o eMBB, nele só os sensores transmitem dados para a central. Com isso a latência se mostrou em todos os casos abaixo de 5 ms. A tabela de conformidade e a CDF apresentam melhor os resultados do cenário isolado.
